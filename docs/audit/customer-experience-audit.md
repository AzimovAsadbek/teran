# Customer experience and catalogue architecture audit

Date: 2026-10-14. Baseline: commit `86535da` on `main` (clean working tree, level with
`origin/main`). Everything below was checked in the code, and the defects marked "reproduced"
were reproduced against the running development stack before any change was made.

Severity: **High** — wrong or unsafe behaviour customers can hit; **Medium** — a real defect with
limited impact or a missing capability the brief requires; **Low** — polish.

## 1. What already exists (verified)

| Area              | Implementation                                                                                                                                                                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sessions          | Opaque 256-bit tokens in an HttpOnly, SameSite=Lax cookie (`__Host-teran_session` over HTTPS); only the SHA-256 is stored; a new token on every sign-in; password change and reset revoke every session (`apps/api/src/auth`).                     |
| Guest cart        | Server-side `Cart` identified by an HttpOnly cookie (`__Host-teran_cart`, 30-day sliding expiry); every change goes to the API, which re-prices and re-validates the cart (`apps/api/src/cart/cart.service.ts`). No browser storage.               |
| Cart on sign-in   | `AuthService.attachCart` attaches the device cart to the account and merges an older account cart into it in a transaction, on both login and registration.                                                                                        |
| Account           | `/account`: greeting, the 20 latest orders, profile form (name, phone, language), password change, sign-out. `/account/orders/[number]`: progress bar and order details.                                                                           |
| Orders            | Purchase-time snapshots in `OrderItem` (name, slug, SKU, size, unit price, line total); customers only read `where: { number, userId }`; guests need the secret token; random, non-sequential numbers.                                             |
| Checkout          | Server-side prices, delivery and totals; stock reserved with a conditional update; idempotency key; profile prefill for signed-in customers; a payment section that lists the methods the API enables.                                             |
| Payments          | `Payment` rows with method, status, amount, provider reference; only `CASH_ON_DELIVERY` exists; staff record the cash (audited). No online provider and no provider abstraction.                                                                   |
| Catalogue         | Flat `Category` (one per product), `Collection` (many-to-many), `Product` with tea-specific columns (format, caffeine, brewing), `ProductVariant` (unique SKU, price, stock), images; filters: category, collection, format, price, stock, search. |
| Security controls | Origin check on state-changing requests, per-route rate limits, strict CSP (`form-action 'self'`, `connect-src 'self'`), Argon2id passwords, audit log for staff actions.                                                                          |

## 2. Findings — customer experience

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                               | Severity | Root cause                                                                                                                                                                                                                    | Affected                                                                                         | Fix                                                                                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | **Delayed, empty sign-in path (reproduced).** The header has no sign-in or registration entry, only an account icon. For a visitor it opens `/account`, which streams an empty dashboard skeleton, asks the API who is signed in, redirects to `/account/login`, which shows a second skeleton while it asks again. Measured with 150 ms latency: form usable 1.06 s after the click. | High     | The header never knows the authentication state; the account icon always targets the protected dashboard; both pages resolve the session inside a streamed boundary, so the redirect happens after a skeleton has been shown. | `components/layout/header-actions.tsx`, `account/page.tsx`, `account/login/page.tsx`, `proxy.ts` | Authentication-aware header (sign-in and registration for visitors, an account menu for customers) resolved on the server in the same response; the proxy sends visitors without a session cookie straight to sign-in. |
| C2  | **Another person's cart on a shared device (reproduced).** When user A's session ends but the cart cookie stays, an anonymous visitor sees A's cart; when user B then signs in or registers on that device, B takes over A's cart and A loses it.                                                                                                                                     | High     | `CartService.findCart` identifies a cart by its cookie token only and ignores its owner; `attachCart` reassigns whatever cart the device holds to the user who signs in.                                                      | `cart/cart.service.ts`, `auth/auth.service.ts`                                                   | A cart is only visible to its owner (a guest cart to anyone holding its cookie); sign-in merges only a guest cart and otherwise restores the account's own cart.                                                       |
| C3  | Cart merge can exceed stock and the line limit; concurrent sign-ins could merge the account cart twice.                                                                                                                                                                                                                                                                               | Medium   | Merge caps quantities only at the per-line maximum; the account cart is read before it is deleted without a guard.                                                                                                            | `auth/auth.service.ts`                                                                           | Explicit merge rules (combine by variant, cap at stock and limits, keep unavailable lines flagged, at most 30 lines); delete-then-merge guarded by the delete count, inside the transaction.                           |
| C4  | No test covers the guest-to-account cart on login or registration.                                                                                                                                                                                                                                                                                                                    | Medium   | Missing coverage.                                                                                                                                                                                                             | `apps/api/test`, `e2e/tests`                                                                     | Integration and end-to-end tests for both flows, retries and shared devices.                                                                                                                                           |
| C5  | Stale session cookie after expiry or revocation is never cleared, so the browser keeps sending a dead token.                                                                                                                                                                                                                                                                          | Low      | The session middleware ignores an invalid token silently.                                                                                                                                                                     | `auth/session.middleware.ts`                                                                     | Clear the cookie when a token is presented but no longer valid.                                                                                                                                                        |
| C6  | Account area is one page: no navigation, no order pagination (20 newest only), no address book, no purchased-products view, no reorder, no e-mail change, no session list.                                                                                                                                                                                                            | Medium   | Not implemented.                                                                                                                                                                                                              | `account/*`                                                                                      | Account layout with overview, orders (paginated, filterable), order detail with timeline and payments, purchases, profile, security (password, sessions), addresses.                                                   |
| C7  | Customers cannot see when their order changed status, only a progress bar.                                                                                                                                                                                                                                                                                                            | Low      | `OrderDto` has no events.                                                                                                                                                                                                     | `orders/order.mapper.ts`, contracts                                                              | Expose status events (dates, no staff notes) and payment attempts in the customer order view.                                                                                                                          |
| C8  | No saved addresses, so returning customers retype the delivery address at every checkout.                                                                                                                                                                                                                                                                                             | Medium   | No model.                                                                                                                                                                                                                     | schema, checkout                                                                                 | `CustomerAddress` model (owner-scoped), address book, address choice at checkout.                                                                                                                                      |

Password reset works only with SMTP configured, and the site already hides it otherwise
(`/auth/features`). It stays as it is: no new flow pretends to reset passwords without e-mail.

## 3. Findings — payments and checkout

| #   | Finding                                                                                                                                   | Severity | Fix                                                                                                                                                                             |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | Only cash on delivery; no provider abstraction, no payment state machine beyond five statuses, no record of payment events.               | Medium   | Provider-neutral payment service with adapters (demo, Click, Payme; card gateway boundary), a documented state machine with enforced transitions, a payment event log.          |
| P2  | Stock is reserved when an order is placed; with online payment an abandoned payment would hold stock for ever.                            | Medium   | Unpaid online payments expire (configurable window); the order is cancelled and stock returned by a scheduled job.                                                              |
| P3  | The CSP allows forms to post only to the site itself (`form-action 'self'`) and the browser to call only the site (`connect-src 'self'`). | —        | Kept. Customers are sent to a provider's payment page by a top-level navigation; providers talk to the API server to server. No CSP relaxation needed.                          |
| P4  | Visa: there is no card acquirer or gateway in the project; showing a Visa logo would not make cards work.                                 | —        | A card method exists only behind a gateway adapter boundary; it is offered in demo mode (labelled) and stays unavailable in live mode until a gateway is chosen and integrated. |

## 4. Catalogue architecture assessment (multi-category brief)

| Topic                    | Current state                                                                                                              | Limitation                                                                                                   | Change                                                                                                                                                                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Categories               | Flat list; the tea types are categories; URL `/catalog/{slug}`.                                                            | No hierarchy (Tea → Green tea), no top-level URLs, no editorial text, slug changes break links.              | `parentId` (two levels), top-level URLs `/{category}` and `/{category}/{subcategory}`, editorial text, reserved slugs, slug redirects; `/catalog/{slug}` redirects to the new address.                                                         |
| Product types/attributes | Tea-specific columns on `Product` (format, caffeine, brewing) and translation fields (ingredients, tasting notes, origin). | Coffee, sweets and gifts need different, validated fields; adding columns per characteristic does not scale. | `ProductType` with typed `AttributeDefinition`s (text, number, yes/no, single and multiple choice; filterable, searchable, visible flags) and `ProductAttributeValue` rows. Existing columns stay as common fields for backward compatibility. |
| Filters                  | Format, price, stock; facets for format and price.                                                                         | No category-specific filters.                                                                                | Attribute facets computed from the products in the current listing; filters in the URL; work with search, sorting and pagination.                                                                                                              |
| Variants                 | `ProductVariant` owns price and stock; SKU unique; conditional stock decrement.                                            | Sound.                                                                                                       | Kept.                                                                                                                                                                                                                                          |
| Order snapshots          | Name, slug, SKU, size, unit price, line total, format.                                                                     | Sound; images come from the live product but fall back gracefully.                                           | Kept; covered by a test that edits and archives a purchased product.                                                                                                                                                                           |
| Gift sets                | A gift set is an ordinary product (format `GIFT_SET`) with its own variant and stock.                                      | Contents are free text.                                                                                      | Kept as a standalone SKU with independent stock (documented); no component stock deduction.                                                                                                                                                    |
| Navigation               | Built from the category list and collections at request time (cached).                                                     | Flat.                                                                                                        | Category tree from the API; new published categories appear without code.                                                                                                                                                                      |
| Admin                    | Category and collection CRUD; product editor with tea fields.                                                              | No parent, no product types, no attributes.                                                                  | Parent and editorial fields; product types and attributes; type-specific fields in the product editor; publish-time validation.                                                                                                                |
| SEO                      | Metadata, sitemap and canonical URLs per page; demo mode `noindex`.                                                        | Category URLs change.                                                                                        | Sitemap and canonical URLs follow the new paths; old ones redirect permanently.                                                                                                                                                                |

Migration policy: additive only. Existing categories become top-level categories with unchanged
slugs; `productTypeId` is nullable, so existing products keep working with their common fields
until a type is assigned. No data is deleted; product IDs, order references and snapshots are
untouched.
